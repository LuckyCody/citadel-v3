=== Tier 8: constant-time (ctgrind) — 2026-07-21, Ubuntu WSL2 ===
valgrind 3.24.0 (rootless build) + libc6-dbg (installed) + ctgrind harness.
Method: mark ML-KEM secret bytes "undefined" via valgrind memcheck client requests,
run decapsulation; any conditional jump on a secret byte = a CT violation.
Build: RELEASE (opt-level=3, overflow-checks OFF). CT analysis must use shipping
code — a debug build adds overflow/bounds-check branches that are false positives.

--- Iteration 1: whole expanded key marked secret (WRONG) ---
43 conditional-jump contexts, dominated by FALSE POSITIVES on the key's PUBLIC
components: sample_ntt rejection sampling [matrix A regenerated from the public seed
inside ek] and a bcmp key-import hash check on H(ek). Both public -> not leaks.

--- Iteration 2: only TRUE secret marked; ek/H(ek) left public ---
Marked dk_PKE [sk_bytes 32..1184] + z [2400..2432]; left ek + H(ek) defined.
Result: 14 conditional-jump contexts, ERROR SUMMARY 3584 errors / 28 contexts.
ALL residual branches localize to:
    ml_kem::algebra::sample_poly_cbd   (algebra.rs:114, 122, 125)
i.e. the CBD noise sampling inside the FO-transform re-encryption, operating on
secret-derived coins. ZERO flagged branches in Citadel's own code
(envelope / kdf / aead / wire) — every residual is in the RustCrypto ml-kem 0.3.2
dependency.

FINDING (honest):
- Citadel's OWN envelope/KDF/AEAD/wire code shows NO secret-dependent branches.
- The residual secret-dependent branches are entirely in ml-kem 0.3.2's CBD sampling.
  This LOCALIZES the key-material timing effect dudect measured (TIMING.md) to a
  specific dependency function, not just "a wobble exists somewhere".
- Leak vs. artifact: the flagged op is a slice bounds-check reached from
  sample_poly_cbd. CBD indexing normally uses PUBLIC loop counters, which would make
  this a memcheck artifact; a genuine secret-indexed access would be a real leak.
  Definitive call needs ml-kem algebra.rs:114-125 source review — the concrete next
  step. Either way it is a property of the ml-kem dependency, consistent with
  RustCrypto's documented "unaudited, not guaranteed constant-time" status.

--- RESOLUTION (ml-kem 0.3.2 source review, algebra.rs:114) ---
sample_poly_cbd ends with:
    Polynomial::new(vals.0.iter().map(|val| Eta::ONES[val.0 as usize]).collect())
i.e. a TABLE LOOKUP indexed by val.0, which is decoded from the PRF output derived
from the (secret) re-encryption coins. So it is a genuine SECRET-INDEXED memory
access — a real constant-time anti-pattern, NOT a memcheck artifact.

Severity for ML-KEM-768 (the parameter set Citadel uses): PRACTICALLY BENIGN.
- param.rs: ML-KEM-768 has eta=2 => ONES = Array<Elem, U16> = 16 entries.
  Elem is u16 => table = 32 bytes, which fits in ONE 64-byte cache line. A
  secret-indexed access therefore touches the same cache line for every index =>
  no cache-timing leak on standard hardware.
- val.0 is a 4-bit decode (0..16) into a 16-entry table => always in range => the
  bounds-check branch never diverges => no branch-timing leak.
- (Note: eta=3 would use a 64-entry / 128-byte = TWO-cache-line table, which WOULD
  be a genuine cache-timing leak — but that is ML-KEM-512's eta1, not the 768 set.)

CONCLUSION: the ctgrind flag is a REAL CT-hygiene finding in the ml-kem 0.3.2
dependency (secret-indexed lookup), but for ML-KEM-768 it is not practically
exploitable (single-cache-line table, always-in-range index) — matching the
"small effect, not exploitable" conclusion in TIMING.md. It is NOT in Citadel's
code. Definitive fix would be upstream (mask-based table selection); Citadel's
options are to accept it (documented, low risk for 768) or pin a future ml-kem
release that makes CBD sampling branch/index-free.
